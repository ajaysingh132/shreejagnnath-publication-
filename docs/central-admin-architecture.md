# GBSBFORYOU AI Publishing Ecosystem
## केंद्रीय एडमिन, स्वतंत्र शाखाएँ और अधिकार व्यवस्था — Architecture v1.0

**स्थिति:** स्वीकृत डिज़ाइन / कार्यान्वयन से पहले समीक्षा हेतु  
**प्रकाशन इकाई:** जगन्नाथ पब्लिकेशन, भोपाल तथा GBSBFORYOU टीम

## 1. उद्देश्य

ई-बुक, ऑडियोबुक, AI वीडियो, YouTube, सोशल मीडिया और ऑटोमेशन को स्वतंत्र मॉड्यूल/शाखाओं में विकसित करना है। हर शाखा में अपना Admin और Sub-admin होगा। एक केंद्रीय Main Admin खाते से सभी शाखाओं तक एक ही लॉगिन के बाद पहुँचा जा सकेगा। मुख्य एडमिन की केंद्रीय नीति और अनुमति जाँच सभी शाखाओं पर लागू होगी।

यह दस्तावेज़ वास्तुकला का प्रस्ताव है; यह अपने आप लॉगिन, डेटाबेस या प्रकाशन API लागू नहीं करता।

## 2. स्वतंत्र शाखाएँ

1. **E-book & Publishing:** पांडुलिपि, संपादन, संस्करण, HTML/PDF/EPUB, मेटाडेटा और पुस्तकालय।
2. **Audiobook Studio:** अध्याय, TTS/रिकॉर्डिंग, ऑडियो फ़ाइलें और निर्यात।
3. **AI Video Studio:** स्क्रिप्ट, दृश्य, मीडिया एसेट, रेंडरिंग और वीडियो आउटपुट।
4. **YouTube Publishing:** शीर्षक, विवरण, थंबनेल, अपलोड ड्राफ्ट, शेड्यूल और प्रकाशित लिंक।
5. **Social Media Publishing:** प्लेटफॉर्म-विशिष्ट पोस्ट, अभियान, स्वीकृति और प्रकाशन स्थिति।
6. **Automation Engine:** Make.com/Webhooks, कतारें, पुनः प्रयास, त्रुटि प्रबंधन और निष्पादन लॉग।
7. **Central Admin & Governance:** पहचान, शाखा पंजीकरण, भूमिका/अनुमति, नीति, स्वीकृति, ऑडिट और सिस्टम स्वास्थ्य।

शुरुआत में इन्हें एक ही रिपॉजिटरी में स्पष्ट मॉड्यूल और अलग रिलीज़ योग्य घटकों के रूप में रखा जा सकता है। स्वतंत्र तैनाती की आवश्यकता आने पर अलग रिपॉजिटरी/सेवा में विभाजित किया जा सकता है।

## 3. पहचान और लॉगिन

- एक केंद्रीय Identity Provider (IdP) SSO प्रदान करेगा; शाखाएँ उसी सत्यापित पहचान को स्वीकार करेंगी।
- हर व्यक्ति का अपना खाता होगा। पासवर्ड या सेशन साझा नहीं होंगे।
- केंद्रीय खाते से सभी शाखाएँ खोलना और प्रत्येक शाखा में स्पष्ट अनुमति के अनुसार काम करना संभव होगा।
- प्राथमिक एडमिन के लिए MFA अनिवार्य रखने की अनुशंसा है।
- OAuth/API access tokens को सर्वर-साइड सुरक्षित रखा जाएगा; उन्हें HTML/JavaScript, GitHub में committed फ़ाइलों या सार्वजनिक लॉग में नहीं रखा जाएगा।
- Firebase के मौजूदा placeholder मान (जैसे YOUR_KEY/YOUR_PROJECT_ID) वास्तविक कॉन्फ़िगरेशन नहीं हैं। मौजूदा लॉगिन/डेटा फ़ॉर्म को उत्पादन-तैयार न माना जाए।

## 4. भूमिका मॉडल (RBAC)

### केंद्रीय भूमिकाएँ
- **Main Admin / Owner:** सभी शाखाओं में अधिकतम प्रशासनिक अधिकार; शाखा Admin नियुक्त/निष्क्रिय करना; वैश्विक नीति, कनेक्शन और अंतिम स्वीकृति नियंत्रित करना।
- **Central Auditor (वैकल्पिक):** केवल लॉग/रिपोर्ट देखना; कोई संपादन या प्रकाशन नहीं।

### शाखा-स्तरीय भूमिकाएँ
- **Branch Admin:** अपनी शाखा के सब-एडमिन, कार्य और शाखा सेटिंग्स का प्रबंधन; केंद्रीय सुरक्षा नीतियों को बदल नहीं सकता।
- **Sub-admin:** केवल आवंटित अनुमति और निर्धारित कार्य-क्षेत्र के अनुसार काम।
- **Editor/Producer (वैकल्पिक):** सामग्री तैयार/संपादित करना, लेकिन भूमिका/यूज़र प्रबंधन या अंतिम प्रकाशन नहीं।
- **Viewer (वैकल्पिक):** केवल देखना और रिपोर्ट पढ़ना।

### मुख्य सुरक्षा नियम
- हर अनुरोध पर सर्वर अनुमति जाँचे; केवल UI में बटन छिपाना सुरक्षा नहीं है।
- डिफ़ॉल्ट रूप से अनुमति नहीं (deny-by-default)।
- शाखा Admin केवल अपनी शाखा में अधिकार दे सके और केंद्रीय Main Admin के अधिकार नहीं बढ़ा सके।
- Main Admin के अधिकार किसी शाखा में भी केंद्रीय पहचान से लागू होंगे, लेकिन सभी संवेदनशील कार्रवाई ऑडिट होंगी।
- किसी भी सब-एडमिन को API secrets, billing या identity-provider settings स्वतः नहीं मिलेंगी।

## 5. प्रकाशन स्वीकृति प्रवाह

**Draft → In Review → Changes Requested / Approved → Scheduled → Published / Failed**

- सार्वजनिक प्रकाशन के लिए मुख्य एडमिन की अंतिम स्वीकृति डिफ़ॉल्ट नियम होगी।
- मुख्य एडमिन लिखित नीति से किसी शाखा/कर्मचारी को सीमित अपवाद दे सकता है; ऐसा अपवाद समय-सीमा, प्लेटफॉर्म और सामग्री-प्रकार के साथ दर्ज हो।
- ऑटोमेशन केवल Approved कार्य चला सकता है। ड्राफ्ट या अस्वीकृत सामग्री प्रकाशित नहीं होगी।
- प्रकाशित सामग्री का URL, प्लेटफॉर्म ID, समय, स्वीकृति करने वाला व्यक्ति और परिणाम सहेजा जाए।

## 6. साझा डेटा और सेवाएँ

प्रस्तावित मुख्य रिकॉर्ड:
- `users`: केंद्रीय पहचान और सक्रिय स्थिति
- `branches`: शाखा ID, नाम, संस्करण और स्थिति
- `branch_memberships`: यूज़र, शाखा और भूमिका
- `permissions`: संसाधन/कार्य पर अनुमति
- `assets`: पुस्तक, ऑडियो, वीडियो, पोस्ट और फ़ाइल मेटाडेटा
- `workflow_jobs`: कार्य, स्थिति, समय और retry count
- `approval_events`: किसने कब स्वीकृति/अस्वीकृति दी
- `publication_records`: प्लेटफॉर्म, बाहरी ID/URL और परिणाम
- `audit_events`: यूज़र, कार्रवाई, संसाधन, समय और परिणाम
- `provider_connections`: कनेक्शन का संदर्भ/स्थिति; वास्तविक secrets सुरक्षित secret store में हों

शाखाओं को केवल आवश्यक साझा डेटा पढ़ने की अनुमति दी जाए। वास्तविक सामग्री और अधिकार रिकॉर्ड पर सर्वर-साइड tenant/branch सीमा लागू हो।

## 7. API/इंटीग्रेशन अनुबंध

हर शाखा को एक समान कार्य-रूप अपनाना चाहिए:
- `createDraft`
- `updateDraft`
- `submitForReview`
- `approve` / `requestChanges`
- `schedulePublication`
- `publishApprovedJob`
- `getJobStatus`

ये अवधारणात्मक नाम हैं; API अभी लागू नहीं हैं। Make.com को केवल प्रमाणित webhook/API के माध्यम से स्वीकृत कार्य भेजने चाहिए। Webhook signature/secret, idempotency key, rate limiting और retry policy लागू हों। किसी बाहरी प्लेटफॉर्म पर वास्तविक प्रकाशन संबंधित आधिकारिक API, OAuth scopes और प्लेटफॉर्म नीतियों पर निर्भर होगा।

## 8. चरणबद्ध कार्ययोजना

1. मौजूदा GitHub प्रोजेक्ट और खुले PR का audit; सक्रिय फ़ाइलों तथा placeholder सुविधाओं की पहचान।
2. तकनीकी stack और central identity provider तय करना।
3. केंद्रीय login, users, branch memberships और server-side RBAC बनाना।
4. एक परीक्षण शाखा के रूप में E-book Library को जोड़ना।
5. audit log और approval workflow लागू करना।
6. Audiobook तथा AI Video मॉड्यूल जोड़ना।
7. YouTube/सोशल मीडिया कनेक्टर और Make.com webhook जोड़ना।
8. permissions, unauthorized access, token handling, duplicate jobs और failed publication के परीक्षण।
9. staging पर सत्यापन के बाद नियंत्रित उत्पादन रिलीज़।

## 9. रिलीज़-पूर्व स्वीकृति मानदंड

- Main Admin एक लॉगिन से सभी अधिकृत शाखाएँ खोल सकता है।
- Branch Admin दूसरी शाखा का डेटा या अधिकार नहीं बदल सकता।
- Sub-admin को केवल आवंटित कार्यों की अनुमति मिलती है।
- बिना स्वीकृति कोई सार्वजनिक पोस्ट/वीडियो प्रकाशित नहीं होता।
- प्रत्येक प्रशासनिक और प्रकाशन कार्रवाई का ऑडिट रिकॉर्ड बनता है।
- कोई secret GitHub या client-side code में नहीं रहता।
- API विफलता पर स्थिति Failed/Retryable दर्ज होती है और डुप्लिकेट प्रकाशन रोका जाता है।

## 10. अगला तकनीकी निर्णय

इस दस्तावेज़ के बाद अगला काम वास्तविक implementation repo की पहचान, मौजूदा auth/database का निरीक्षण और उसी के अनुरूप central identity + RBAC का पहला MVP बनाना है। इस दस्तावेज़ को लागू सिस्टम का प्रमाण न समझें।
